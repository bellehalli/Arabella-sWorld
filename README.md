## Run and test

`npm ci --ignore-scripts`, then `npm test`.

Deploy to Vercel with framework Other, no build command, and project root as output. `/api/config` is a Node function. A generic static server alone needs to serve `/api/config` as `{ "enabled": false }` for device-only mode. No preview server was launched in the managed workspace.

The application itself is browser-native ES modules. The pinned Supabase client is bundled in vendor/supabase.mjs. `npm run build:sdk` rebuilds it from the pinned lockfile. Linkedom is only a test dependency, not a browser dependency. Google Fonts is optional with local system-font fallbacks.

## Storage and privacy

Device-only state: an AES-GCM envelope at `arabella-dreamhub-v2` in localStorage, unlocked by the local vault. Drafts use encrypted envelopes at `dreamhub-draft:local:<record or type>` or account-scoped draft keys in cloud mode. The old `belle-dreamhub-v1` key is never changed. Export format is versioned JSON `{format, exportedAt, state}`. Import validates first, previews additions, identical IDs and conflicts; approved imports add only new records, preserve current conflicts and record provenance. Legacy v1 migration preserves raw source fields and ledger provenance. It does not invent missing dates or habit history. Local multi-tab writes use Web Locks when supported; fallback is best effort and should not be treated as a distributed database lock.

Trash is retained until manually purged. Deleted or old snapshots may also exist in exported backups. Writing history is bounded to ten prior versions. Photos consume localStorage capacity; a failed storage write leaves the editor and draft available, never claims a committed save.

Device-only workspace records and drafts are encrypted at rest by the local vault while locked, using a passphrase and separately saved recovery code. A concealed search preview is not a security boundary. Cloud records are not end-to-end encrypted. Encrypted backup files use a separate passphrase that cannot be recovered; full restore replaces the current workspace only after an explicit confirmation. No bank feed, analytics provider, AI API, outbound messages, purchases or financial transactions are connected.

Cloud attachments use the private `dreamhub-attachments` Storage bucket and owner-scoped `dreamhub_attachments` metadata. The storage key is an owner UUID folder plus a random file UUID; the original filename is metadata only. Browser code checks the file signature and size, while the bucket limits size and MIME types. Encrypted full backups can include up to 14 MB total of attachment files; those bytes are encrypted in the exported file but cloud attachment bytes are not end-to-end encrypted. Restore previews record and attachment counts, skips content-identical attachment files by SHA-256, and keeps differing same-name files as separate copies. Apply `database/002_private_attachments.sql` only to an isolated staging project until the full acceptance checklist passes.

## Managed auth / cloud activation (coded, NOT provisioned or live-tested)

1. Review current provider free-tier limits, data terms, storage requirements, quotas and email delivery before provisioning. No paid tier is required by the code; perpetual $0 operation is not promised.
2. Provision a dedicated staging Supabase project. Disable public signups. Configure email OTP template to provide Token, not only a magic link; verify delivery for the owner. Invite the one intended owner through the managed Auth UI. Do not invent auth or cryptography.
3. Apply `database/001_private_sync.sql`, then `database/002_private_attachments.sql` in staging only. As an administrator, insert the verified invited auth.users.id into dreamhub_owners. Never ship an owner UUID based on an email guess.
4. Run `npm run staging:smoke` for the state/RPC authorization check and `npm run staging:attachments` for the temporary attachment lifecycle test. Both hard-reject the known production project ref; the attachment check uploads and then deletes a harmless text probe.
5. For a local UI smoke check, run `npm run staging:preview`. It asks for the exact staging URL and a modern `sb_publishable_…` key, then serves the app only at `127.0.0.1:4173`. It does not deploy or alter Vercel. The sign-in screen accepts the emailed one-time code. Never use a secret or service-role key.
6. For a hosted Preview, set only the staging SUPABASE_URL and SUPABASE_PUBLISHABLE_KEY in the Vercel Preview environment, then deploy the candidate branch as a Preview. Never add staging keys to Production variables. Test owner email-code login, anonymous denial, other-account denial, attachment preview/download/deletion, save on two devices, conflict retention, sign-out, export, backup restore, and quota/network failure. Snapshot writes use an atomic, owner-scoped RPC with expected revision. This is a foundation snapshot store, not the final normalized v5 per-record database schema.
7. Import any local review data manually after exporting it. There is no automatic upload of browser-local content. Cloud mode keeps editor drafts on-device and queues offline editor record saves for reconnect. Other cloud mutations still require a connection. Revision conflicts stay queued for a deliberate keep-cloud, save-copy, or replace choice. Failure to check cloud configuration blocks access rather than silently falling back to local mode.
8. Enable production only after reviewing this exact staged candidate and passing the real authorization and restore tests.
